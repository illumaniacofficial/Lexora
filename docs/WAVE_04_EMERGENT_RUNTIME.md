## Runtime architecture

Lexora is **one root full-stack Node process**. It serves the SPA, `/api/*`, and
`/uploads/*` from a single server. There is no separate frontend or backend app.

- Working directory: `/app`
- No dotenv loader in the app — environment must be injected by the
  platform/process environment (the repo's `.env` is git-ignored and never committed).

### Development

```bash
npm run dev
```

### Production

```bash
npm run build
npm run start
```

### Port

The port is read exclusively from the `PORT` environment variable
(`server/config/env.ts` → `Number.parseInt(env.PORT || "5000", 10)`).
Emergent/platform configuration must supply `PORT`; do not hardcode a port in the repo.

## Production database requirement

The local `lexora_emergent` PostgreSQL database (and any pod-local PostgreSQL) is
**development/preview only**. Pod-local databases are ephemeral and must not be
treated as production infrastructure.

**A persistent, externally managed PostgreSQL database must be supplied through
`DATABASE_URL` before production deployment.** Lexora uses standard PostgreSQL and
Drizzle; no database-code rewrite and no Supabase client libraries are required —
only a new, persistent `DATABASE_URL`.

## Production PostgreSQL initialization procedure

Run once against a fresh, empty, persistent database.

1. Supply production `DATABASE_URL` in the platform environment (never commit it).
2. Verify database target identity — host, port, and database name, and confirm it
   is the intended persistent instance (not a pod-local database).
3. Run `npm run db:push` **once** against the new empty database.
4. Confirm the expected tables exist (core: `users`, `session`, `projects`,
   `chapters`; plus the Wave 03 revival tables, ~48 total).
5. Set required production secrets: `SESSION_SECRET` (≥32 chars),
   `ADMIN_INITIAL_PASSWORD`, plus the API keys for enabled integrations.
6. Run the production build: `npm run build`.
7. Start Lexora: `npm run start`.
8. Verify `/` returns `200`.
9. Verify `/api/auth/me` rejects unauthenticated access (`401`).
10. Verify admin bootstrap/login succeeds.
11. Confirm no destructive seed behavior occurs — seeding must log that data
    already exists and skip (the seed never deletes or resets live data).

> `db:push` is a schema-sync tool. Run it once against the empty target and
> review its output before re-running against any database that holds data.
